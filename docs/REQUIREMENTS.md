# HX-CentCom requirements and test coverage

This page maps each owner requirement of work unit WU1 to the feature that meets it and to the tests that check it. Report this coverage apart from test counts. A passing suite does not show that a requirement is met. [Issue #1](https://github.com/HX-Infratstructure/HX-CentCom/issues/1) tracks the work unit.

## Status values

- **built**: the feature is in this tree.
- **tested**: automated tests in this tree check it. The pull request records the run, its commit, and its result.
- **live PASS**: a check on the deployed app exercised it. The cell names the check, its UTC date, the release it ran on, and its GitHub record, and says what the check left out.
- **live NOT_RUN**: nobody has checked it on the deployed app yet. The app has run on HX-15 behind the HX-7 route since GO-1 to GO-4 on 2026-11-14 ([owner GO](https://github.com/HX-Infratstructure/HX-CentCom/issues/1#issuecomment-6875640539), [OPERATIONS.md](OPERATIONS.md#deploy-to-the-hx-hosts)).

## Deviations and additions

These are CC1's decisions, not owner rulings:

- **The kanban filters by repository.** The spec asks for an agent and program filter, and the data model has no program field, so the board filters by agent and repository.
- **The kanban shows the whole task set,** with no 20-row default and no Show more. The seed creates seven tasks, and `createTask` adds one per piece of work an agent registers, so the set grows through the API and nothing bounds it.
- **The spec's "No page ever loads a whole table into the browser" is only partly met.** The workspace read still carries tasks, requirements, agents, status labels, repository heads, and every Pending decision whole ([API.md](API.md#get-apiv1workspace)). Requirements are not a set that no API creates, because `setRequirement` adds them. [ARCHITECTURE.md](ARCHITECTURE.md#boundary-exceptions) gives the reason for each set except the decisions. Any key can request a decision, and the overview lists every Pending decision under "Needs your decision" (`src/routes/index.tsx`), so the workspace carries them all.
- **Three additions stay:** the MCP tool `list_updates`, the CLI commands `centcom raid update` and `centcom lesson update`, and the `superseded_by` column, which the API never sets.
- **A `system` update has no source,** and the pages label it "System" with the agent whose write triggered it.
- **Closing a dependency on another agent's task is 403** for an agent that is not the owner (P2-1), and so is pinning a dependency to it.
- **`src/start.ts` reuses `scripts/secret-file.ts`,** so the app and the scripts share one reader of mode-600 secret files.

The plan's F5 says that a database trigger writes the log row. As the spec's data model says, the services write each activity row in the same transaction, and the database trigger refuses any change to the log.
