# HX-CentCom architecture

This page describes how HX-CentCom is built: which component owns what, the data model, how agents are identified, what the system does on its own, and where it runs. It is the responsibility map that [AGENTS.md](../AGENTS.md) requires. When a change adds a component or a public interface, it adds the row here.

## Request paths

Each caller reaches PostgreSQL through the service layer in `src/server/services/index.ts`:

- **Pages.** The routes `/`, `/tasks`, and `/decisions` load data through the server functions in `src/lib/tasks.functions.ts`. The routes `/raid` and `/lessons` each define one GET server function. Every server function calls the services.
- **REST.** Agents call `/api/v1`. Each route file in `src/routes/api/v1/` makes one service call through `src/server/http/endpoint.ts`.
- **MCP.** Agents call `/mcp`. `src/routes/mcp.ts` passes the request to `src/server/http/mcp.ts`, where each tool makes one service call.
- **CLI and hook.** `bin/centcom` and `bin/centcom-hook` call the REST API over HTTP.
- **Key issuing.** `scripts/issue-key.ts` opens its own database connection and calls the services.
- **GitHub sync.** `scripts/github-sync.ts` reads GitHub and writes the two GitHub tables through `recordGithubSnapshot`.

What the pages show:

- **Overview.** Open tasks list the blocked ones first, then the unfinished ones, each in workspace order, and leave out finished tasks that nothing blocks. Open pull requests show the first eight, and the heading counts all of them. Pending decisions follow the inbox order below.
- **Tasks.** The board has four columns in workflow order, one per `group`, each with its card count. Its agent filter applies to the whole page and comes from the URL, as in `/tasks?agent=CC1`. The Gantt timeline spans whole weeks, from the Monday on or before the earliest planned date to the Sunday on or after the latest. A task with only one planned date widens that window but gets no bar.
- **Decisions.** The pending inbox lists the decision that blocks the most tasks first, then the oldest request, and a decision with no recorded request last. History lists decided, deferred, and superseded decisions, the newest decision first. The sheet shows its Options section only when the decision has options.
- **Show more.** The line under a list reads, for example, "Showing 2 of 3 updates.", "Showing all 3 updates.", or "Showing 1 update." for a single item. Its error line stays plural, as in "Could not load more lessons."
- **RAID register.** Type tabs (risk, assumption, issue, dependency) and chips for severity, status, owner, and task, each with its count. Each row shows the title, summary, type, severity, status, review date, owner, and tasks. The sheet adds the facts of the item's type, the severity with its rater, the decision, the creator, and the source. A dependency's "Waiting on" fact shows a `task:<id>` or `decision:<id>` blocking ref as an in-app link to that record's sheet, an http or https URL as an external link, and any other value as plain text.
- **Lessons.** Status and tag chips. Each row shows the title, summary, status, tags, and, for an adopted lesson, its enforcement link. The sheet adds the situation, action, outcome, recommendation, applies-to, creator, and source.
- **Record links.** A link to a task, decision, RAID item, or lesson opens that record's sheet on its own route, such as `/raid?item=RAID-07`. On the record's own route the link keeps the page's filters. From another route it carries only `item`.
- **Sources.** An `hx15:<path>` source shows its path and "local to HX-15". A row shows only the file name.
- **Pull requests.** The overview lists open pull requests only, unlabeled. `PR_STATE_LABELS` gives `closed` "Closed", `merged` "Merged", and `gone` "Gone (404 on GitHub)", and a state the UI does not know shows its raw text, never "Open". No page lists pull requests that are not open, and no route uses the `lists.prs` contract.
- **Update origin.** An update from an agent shows the agent's badge and "<kind> via <source>", such as "Progress via CLI". A `system` update, or any update with no source, shows a neutral "System" mark and "after <agent>'s change", naming the agent whose write triggered it.

## Boundary exceptions

No known application code breaks the boundaries in [AGENTS.md](../AGENTS.md) at this commit. `tests/raid/schema.test.ts`, `tests/raid/seed.test.ts`, `tests/final/migrations.test.ts`, and `tests/final/seed.test.ts` cross one on purpose, because they import modules of `src/server/db/` to test the database component's own contract: its columns, CHECK constraints, migrations, and seed. Two tests check the boundaries: `tests/fixround/services-boundary.test.ts` for `src/lib`, `src/routes`, and `src/components`, and `scripts/tests/public-surface.test.mjs` for `scripts/`.

One read is not bounded. `listWorkspace` returns tasks, requirements, decisions, agents, pull requests, and repository heads whole, and only its updates are paged. The pages load it through `tasksQuery` in `src/lib/task-data.ts` and refetch it every 30 seconds.

## Data model

`src/server/db/schema.ts` defines the core tables, `src/server/db/schema-raid.ts` defines `raid_items` and `lessons`, and `drizzle/migrations/` creates them all. Every timestamp is an ISO 8601 UTC string, such as `2026-11-14T09:00:00.123Z`, and every connection must use the UTC session settings in `client.ts`, or reading a timestamp fails. A column that a source may lack is nullable, and null means "not recorded".

Decision ids are `D-` and a number of at least two digits, such as `D-07` or `D-100`, drawn from `owner_decision_id_seq`. RAID ids are `RAID-NN` from `raid_item_id_seq`, and lesson ids are `L-NN` from `lesson_id_seq`.

`RAID_TYPE_FIELDS` gives each type its own columns. A risk has `probability`, `impact`, and `mitigation`. An assumption has `validation_method` and a required `validation_state` (`unverified`, `validated`, or `invalidated`), which is `unverified` when a new assumption gives none. An issue has `impact`, `resolution`, and `escalated`. A dependency has a required `blocked_task_id` and a required `blocking_ref`. A RAID item's type never changes.

### Computed values

- **Progress.** A task's progress is the count of its `PASS` requirements over all its requirements. `percent` is that ratio rounded to a whole number, and null when the task has no requirements. No table stores progress, and posting progress or setting a requirement with a typed `progress` field fails with 400.
- **Group.** A status update sets the task's group: a status whose `is_done` is true gives `done`, `In progress` gives `in_progress`, `Waiting` gives `backlog`, and `Ready for owner` gives `ready_for_owner`. Any other status, such as `Blocked`, keeps the current group.
- **Version.** Each write adds 1 to the version of the task, decision, RAID item, or lesson it addresses. A write that sends the version it read, in `If-Match`, fails with 409 when another write came first. Closing a dependency that unblocks a task also adds 1 to that task's version.

### Seed

`npm run db:seed` loads the agents, the five status labels (`Waiting`, `In progress`, `Complete`, `Blocked`, `Ready for owner`), seven tasks, their requirements, and the decisions `D-01` to `D-17`. The header of `src/server/db/seed.ts` names the source of each value. A value that no source gives is null. No seeded decision records options or a recommendation, because no source gives them, and `D-03` is the deploy GO alone, because `D-17` is the Run 2 GO.

The same transaction loads `RAID-01` to `RAID-08` and `L-01` to `L-09` from `src/server/db/seed-raid.ts`, each with its source. CC1 rated each seeded RAID item's severity, so `severity_rated_by` is `CC1`, and `CC1_SEVERITY_RATINGS` holds the reason for each rating. No seeded issue is high or critical. `created_by` is null on seeded rows, because no agent created them.

## Identity

There is no login. Each agent proves who it is with its own bearer key, and the server records that agent as the author of every write.

- **Agents.** `CC1`, `CC2`, `Codex`, and `OpenCode` have role `agent`. `Agent Zero`, the owner, has role `owner`.
- **Key format.** A key is `hxc_<slug>_<32 characters>`. The slug is the agent id in lowercase, with each run of other characters turned into `-`: `CC1` gives `hxc_cc1_...`, and `Agent Zero` gives `hxc_agent-zero_...`. The 32 characters are 24 random bytes in base64url.
- **Storage.** `agent_keys.key_hash` holds the SHA-256 of the key in hex. The plaintext exists only in the return value of `issueKey`, which the API shows once. It is never stored, logged, or kept for a replay, so key writes take no `Idempotency-Key`.
- **Resolution.** `resolveActor` accepts `Authorization: Bearer <key>` when the key has the format above, its hash matches a key that is not revoked, and its agent is active. Otherwise the caller has no actor.
- **Attribution.** The server stamps the actor on `task_updates.agent_id`, `activity_log.actor`, `owner_decisions.requested_by`, `task_requirements.updated_by`, `raid_items.created_by`, `raid_items.severity_rated_by`, and `lessons.created_by`. The REST API drops any author field in the request body, and the MCP tools refuse it as an unknown argument.
- **Permissions.** Reading needs no key. A write without a valid key fails with 401. `POLICY` in `services/policy.ts` decides the rest: an agent posts progress and sets requirements only on tasks whose `agent` is itself, any key may request a decision, and only the owner decides, issues keys, and revokes keys. The owner may write any task. Any key may add a RAID item or a lesson. An agent changes only the RAID items whose `owner_agent` or `created_by` is itself and the lessons it created, so on seeded rows, where `created_by` is null, it changes only the RAID items it owns. The owner may change every RAID item and lesson.
- **First owner key.** `scripts/issue-key` calls `bootstrapOwnerKey` to issue the first owner key. It works only while no owner key is active, and no request path reaches it. Later keys go through `issueKey` with the owner's key.
- **Owner mode in the UI.** The owner pastes the owner key once per browser tab. The page keeps it in `sessionStorage` and sends it as the bearer key when the owner decides.
- **Trust.** CC1 and CC2 both run as the Unix user `hxsa` on HX-15, so each can read the other's key file. A key records which agent did the work. It is not a security boundary, which the owner accepted for DEV/TEST.

## Automations

These changes happen without a separate request. Several of them post a `system` update on a task. A `system` update has no `source`, its `agent_id` is the agent whose write triggered it, and the pages show it as "System" with the triggering agent named, instead of a source ([Pages and UI components](#pages-and-ui-components)).

- **Every write by an agent or the owner** adds exactly one `activity_log` row, with the actor and the values before and after, in the same transaction. A refused write adds none. The GitHub sync's writes add no row, because the sync is not an agent.
- **Deciding a decision** posts one `system` update on each existing task in its `blocks` list. The note is `<decision id> <status>: <decision text>`, and the update links to the decision source. The blocked tasks' versions do not change.
- **A status in a progress update** sets the task's `status` and `group` in the same transaction.
- **Setting a requirement** recomputes the task's progress and returns it.
- **The GitHub sync** runs every 5 minutes from `hx-centcom-github-sync.timer`. It reads the non-archived repositories of the HX-Infratstructure organization with GET requests, with each default branch's head, the open pull requests, and the pull requests merged or closed in the last 30 days. It fetches each stored open pull request that left the open list, and marks it `gone` when GitHub answers 404. It keeps `merge_commit_sha` only for merged pull requests.
- **The Claude Code hook** posts a `link` update after a successful `git push`, `gh pr create`, or `gh pr merge`. [AGENT-POSTING.md](AGENT-POSTING.md) lists when it posts and when it stays silent.
- **A high or critical issue opens a decision.** After a RAID write, `openIssueDecision` in `services/raid.ts` checks the stored item. If it is an issue, its severity is `high` or `critical`, its status is not `closed`, and its `decision_id` is null, the write opens a pending decision with `gate_type` `policy` and links it through `decision_id`. The decision copies the item's summary, description, and source, and the actor is its requester. An issue that already has a decision opens none, so a repeat or a replay never opens a second one. The RAID write's one activity row records the new decision id under `after.effects`.
- **Closing a dependency clears only a `dependency` block.** When a dependency moves into `closed`, `closeDependency` in `services/raid.ts` locks its blocked task. It sets the task's `blocked_on` to `none` only when `blocked_on` is `dependency` and no other open dependency blocks the task, and then adds 1 to the task's version. A task blocked on `owner_decision` or `assignment` stays blocked. Every such close posts one `system` update on the task, `<RAID id> is closed.` followed by the outcome: the task is unblocked, the task is not blocked, the task stays blocked because other dependencies are still open, or the task stays blocked on its other block. In the seed, `RAID-05`, `RAID-06`, and `RAID-07` block `IRP-04`, whose `blocked_on` is not `dependency`, so closing them leaves it blocked.
- **A task that becomes done asks for lessons.** `postProgress` runs through `withLessonsAsk` in `services/lessons.ts`. When a progress update moves a task from a status that is not done to a done one, such as `Complete`, the same transaction posts one `system` update that asks the task's agent to add lessons through `POST /api/v1/lessons` or the MCP tool `add_lesson`.

## Deploy topology

The deployment is DEV/TEST, and each host step needs the owner's GO ([OPERATIONS.md](OPERATIONS.md)). Requests take this path:

1. Agents and browsers send requests to `http://192.168.50.207:8420`, the HX-7 NGINX server block in `deploy/hx7/hx-centcom.conf`. It has no TLS and no authentication, and it turns off proxy buffering and allows a 300-second read timeout, so MCP responses stream through.
2. NGINX passes each request to `192.168.50.215:5420` on HX-15, where the systemd user unit `hx-centcom.service` of the user `hxsa` runs `node .output/server/index.mjs` from the `current` release.
3. The app reads `DATABASE_URL` from `~/.config/hx-centcom/app.env` and connects to the database `centcom`, owned by the role `centcom_app`, on HX-9 at `192.168.50.209:5432`.

On HX-15, `hx-centcom-github-sync.timer` starts `hx-centcom-github-sync.service` every 5 minutes. The service reads the GitHub token from the file that `GITHUB_TOKEN_FILE` names, sends GET requests to `api.github.com`, and writes to the same database. Releases live in `~/.local/share/hx-centcom/releases/<sha12>/`, with the links `current` and `previous` beside that folder. [deploy/hx15/README.md](../deploy/hx15/README.md#know-the-paths-and-names) lists every path and name.
